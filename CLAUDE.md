# u2b-ukan — ERP-ядро + CRM «Улкан» (торговля/производство металлом)

> Читать ПЕРВЫМ в каждой сессии. Планы: `PLAN.md` (ERP-ядро), `ULKAN-PLAN.md` (оперативка/канбан),
> `docs/PRODUCER-BRANCH.md` (поток лист→изделие), `docs/SCHEMA.md`. Память сессий: `~/.claude/.../memory/`.

## Стек и деплой
- **Next.js 14** (App Router, `--src-dir`) + TS + Tailwind + **Neon Postgres** (pooler) + **Drizzle ORM** + Zod.
- Код в папке **`nextjs/`** (не в корне). Деплой **Vercel** (Root Directory = `nextjs`), ветка **`master`**.
- Репозиторий публичный `github.com/ulan1988/u2b-ukan` — секреты только в `nextjs/.env.local` (в .gitignore).
- `.env.local`: `DATABASE_URL`, `AUTH_SECRET` (значение в **одинарных кавычках** — при парсинге в скриптах снимать кавычки и `\r`).

## Метод (СТРОГО по слоям)
`route (app/api/**) → dto (zod) → service (бизнес-логика) → repository (только Drizzle) → db`.
- Компоненты НЕ вызывают fetch напрямую — через `lib/api/*`. UI-токены: `lib/colors`, формат: `lib/adminFmt`.
- Номера документов: `lib/num`. Даты — локальный день (`today()`), не UTC-срез.
- Справочники (products/contragents/warehouses/users) — общие; Улкан НЕ дублирует, только FK.
- **Цены продажи — ПО ОРГ** (`product_prices` orgId+productId: розница/опт/спец): `products` = общий ШАБЛОН (имя/дерево/тип + **закуп `priceIn` общий**), а цены продажи свои у каждой орг (головной свои, филиал свои, друг на друга НЕ влияют; нет строки → 0 «впишите в чеке», цена другой орг НЕ подставляется). Чтение — `refs.listProducts(orgId)`/`listAllProducts(orgId)` накладывают `product_prices` (иначе розница/опт/спец = 0); `/api/refs` и `/api/products` берут орг из `?orgId` иначе сессии; `/api/pricing` (GET/POST) тоже орг-зависим. Запись — `catalog.service.editProduct/addProduct(…, orgId)` и `pricing.service.setItemPrice(…, orgId)` пишут в `product_prices[orgId]`. Номенклатура (`NomenclatureScreen`) правит цены ВЫБРАННОЙ в шапке орг (`useAdmin().orgId`, бейдж «💰 цены: {орг}»); имя/дерево/закуп — общий шаблон. Миграция: старые цены продажи ушли головному, шаблон `products` обнулён по продаже (закуп сохранён).

- **ОБЩАЯ — ТОЛЬКО НОМЕНКЛАТУРА-ШАБЛОН; СКЛАД СВОЙ У КАЖДОЙ ОРГ (правило 13.11.2026).** Общий у всех — только шаблон (базовые товары: имя, дерево, ед.; цены продажи всё равно по орг). Склад головного и каждого филиала — СВОЙ и складывается ТОЛЬКО из прихода и расхода (`stock_movements`). Поэтому собранный товар (база + цвет/см: «Изделие 7024 19 см») — НЕ шаблон: флаг `products.variant`, в экране «Номенклатура» он не показывается (роут `/api/products?template=1` → `listProducts/listAllProducts(orgId, templateOnly)`), а виден на складе той орг, куда пришёл. В КАТАЛОГАХ ВЫБОРА товара (касса, накладная, пикеры) варианты остаются — иначе не оформить первую приходную. Флаг ставят `producer.service.ensureProduct` (имя кончается «N см») и `invoice.service.ensureVariantProduct` (всегда). **ВАРИАНТ = БАЗОВЫЙ ТОВАР + ЛЮБОЙ ХВОСТ** (цвет RAL, «дерево», «2,5м», «N см»): в шаблоне остаются только базовые без цвета. Разовая разметка 13.11.2026: 57 карточек «база + [цвет] + N см», затем ещё 48 в «Комплектующих» (H/J-профиль и углы по цветам и длинам) — в шаблоне «Комплектующих» осталось 13 базовых (+2 «Изделия №…» и 5 архивных), а в каталоге выбора их по-прежнему 83. Товара без базового имени разметка НЕ трогает.
- **Владелец номенклатуры (правило 10.11.2026):** товар/папку, заведённую **филиалом**, видит ТОЛЬКО он; заведённое **головным (Адал Строй 2)** — общее для всех орг. Поля `products.owner_org_id` и `nom_folders.owner_org_id` (NULL = общее), проставляет `refs.repo.ownerOrgFor(orgId)` (орг `hq` → NULL, филиал → свой id) при `addProduct`, `createFolder`, `ensureProduct(name, orgId)`. Чтение: `listProducts(orgId)`/`listAllProducts(orgId)`/`listFolders(orgId)` = общие + свои; БЕЗ orgId фильтра нет (служебные вызовы — автозакуп, материал, раскрой — видят всё). Старые товары/папки остались общими.

## Организации (прод-база)
- **Адал Строй 2** `hq` (бывш. «U2B головной», переименован окт. 2026) — `e015c65a…`, склад Центр-Склад.
- **Нипа листогиб** `producer_seller` (филиал-производитель) — `50d5113c…`, «Склад производителя».
- **Магазин Кристалл** `seller` (филиал-продавец) — `6673fad6…`, склад «Склад Кристалл», свои контрагенты (перенесены из 1С «КРИСТАЛЛ 2025», 90 шт).
- Мосты меж-орг: `contragents.orgRefId`. Плечо позиции: `leg` (1 = поставщик-филиал/производство, 2 = обычная), по совпадению имени пользователя-branch и контрагента (`lib/legDetect`). **Прямой заказ мастера (`prodOrder`) поставщика не имеет — его позиции по умолчанию `leg=1`** (иначе карточка не попадает на стол мастера и `sendPositions` отвечает «Нечего отправлять»). `addPosition` без поставщика наследует `leg` соседей по карточке. **Форма заказа кабинета** (`POST /api/client/orders`, не `prodOrder`) уходит в книгу **ГОЛОВНОГО** (org kind='hq'), заказчик = мост-контрагент ГО на орг кабинета (`contragentByOrgRef`) — так головной получает заявку филиала/клиента и собирает автозакуп. `prodOrder` (заказ мастера на производство) остаётся у филиала (свой цикл).
- **ГЛАВНОЕ ПРАВИЛО «заявка от имени заказчика» (`createOrder`):** любая продажа на контрагента, **принадлежащего головному** (`contragentOwner().ownerKind==='hq'`), автоматически уходит в **книгу головного** → попадает в **автозакуп** (`saleDemand(hq)`), даже если создана из филиала (Нипа) или у заказчика НЕТ кабинета. Оформляется как заявка самого заказчика (`fromName` = имя контрагента, `fromId` = его кабинет если есть). Исключения (остаются в своей орг): касса магазина (`source='cashier'`), карв спецпроекта (`specProjectId`), заказ мастера (`prodOrder`). Так и головной (Адал Строй 2), и филиал постоянно оформляют заявки от клиентов, и они сразу видны в автозакупе на сайте.
- **ПРИХОДНАЯ С ПОЛУЧАТЕЛЕМ — ДОМИНО ОДНОЙ КНОПКОЙ (правило 11.11.2026):** в приходной головного есть поле **«Получатель»**; указал и провёл → товар не залёживается: (1) приход на Центр-Склад, (2) сразу **расходная на получателя ТОЙ ЖЕ ДАТОЙ**, (3) если получатель — филиал (мост `org_ref_id`), у него **приходная тем же днём, с ценой**. **Цена отгрузки — обычная цена продажи этого контрагента** (`contragents.price_type`: спец → опт → розница из прайса своей орг `product_prices`, через `refsRepo.productsWithOrgPrices` + `priceForClient`) — то же, что при продаже логистом; цены продажи у орг нет (0) → берём цену прихода, чтобы не отгрузить за 0. Новых сущностей нет: `recipientId` в `createPurchaseSchema` → `document.service.shipToRecipient` (вызов в конце `createPurchase`) → обычный `createSale` → его зеркало. Форма: `DocCreateForm` (вид `in`) показывает получателя и подсказку «приход → расходная … на N ₸ (его цены) → у него приходная тем же днём».
- **НАКЛАДНАЯ ЗАДНИМ ЧИСЛОМ ⇄ ЗЕРКАЛО ФИЛИАЛА (правило 11.11.2026):** головной вправе провести накладную любым прошедшим днём, и у филиала она **приходуется ТЕМ ЖЕ ДНЁМ**. Смена (закрытие дня) этим накладным не мешает — это не чек, они просто отражаются в отчёте своей даты. **РЕШАЕТ ДАТА, А НЕ ПОРЯДОК ВВОДА:** приход, внесённый позже, встаёт в свой день и становится первым по дате, продажа — после него; проведение задним числом НЕ блокируем и минус остатка НЕ запрещаем (движения считаются по `stock_movements.date`, запретов на минус в накладных нет и добавлять не надо). Себестоимость FIFO (`doc_links`) по уже проведённым продажам задним числом НЕ пересчитывается — **так и оставляем** (решение владельца 11.11.2026: «тут проблем нет»), пересчёт связок по дате не делать. Ручная накладная на мост-контрагент (`contragents.org_ref_id`) зеркалится в книгу второй орг противоположным типом (`document.service.mirrorBetweenOrgs`, `parent_doc_id`): у зеркала та же `date`, движения склада тоже этой датой; по времени создания отгрузка идёт раньше прихода (при зеркале приходной время сдвигается на −2 с прямо в SQL). **ПЕРЕНОС ДАТЫ = ДОМИНО ПО ВСЕЙ ЦЕПОЧКЕ (11.11.2026):** правка `date` ЛЮБОГО звена (`updateDocument`) переносит день всей связанной цепочки и дат её движений (`docRepo.setMovementsDate`): поднимаемся к корню и идём вниз по обеим связям — зеркала филиалов (`parent_doc_id`) И отгрузка получателю из приходной (`documents.origin_doc_id`, ставит `shipToRecipient`). Служебная `chainDocs(docId)` в `document.service`, в журнал каждого документа пишется «дата по цепочке: было → стало», наверх возвращается `dateMoved`. Без связи `origin_doc_id` отгрузка получателю оставалась на старой дате — филиал видел другой день. «Применить всем» (`docSync.applyToChildren`) тоже выравнивает день дочерней по матери, но цены шлёт только по `parent_doc_id` (на отгрузку получателю не лезет — там свои цены продажи). Карточные накладные (`sourceOrderId`) зеркалятся своим механизмом в `invoice.service` — `mirrorBetweenOrgs` их не трогает (иначе дубль). ⚠️ По [[Правилу Домино]]: задний день меняет остатки на дату, кассу дня и уже закрытую смену обеих орг, а себестоимость FIFO (`doc_links`) по ранее проведённым продажам задним числом НЕ пересчитывается.

- **НАЧАЛЬНЫЕ ОСТАТКИ И ДАТА ОТСЕЧЕНИЯ (правило 11.11.2026).** Сальдо контрагентов из 1С лежит в `contragents.opening_balance` (+ нам должны, − мы должны), день переноса — в `organizations.opening_as_of` (Адал Строй 2, Нипа и Кристалл = **01.11.2026**). Долг = **нач. остаток + документы и оплаты С ДАТЫ ОТСЕЧЕНИЯ**: всё, что датировано раньше, в долг не идёт — оно уже внутри остатка (иначе документы 19–25.10 задваивали сальдо). Фильтр в `finance.repo` (`totals`, `contragentBalances`) и `fin.repo.contragentOpenInvoices`. **Даты остаются мягкими** — задним числом проводим как раньше, правило только убирает задвоение. У филиалов **с нуля только ДЕНЬГИ** (счета Нипы и Кристалла на 01.11.2026 = 0), а **долг перед Адал Строй — как у любого контрагента** (уточнение владельца 13.11.2026): начальный остаток на мост-контрагентах = долг на закрытие дня **31.10.2026** из 1С, в книге ГО со знаком + (нам должны), в книге филиала со знаком − (мы должны); дата отсечения у филиалов тоже 01.11.2026. Залито: Магазин Кристалл **18 417 121,25** (акт сверки 1С; сверка на 01.11: 18 417 121,25 + 1 250 000 − 565 350 = 19 101 771,25 — совпало с 1С до копейки), Нипа листогиб **4 303 500** (по документам нач. остатка товара — ждёт сверки с актом 1С). Считать долг филиала по стоимости завезённого товара НЕЛЬЗЯ — в 1С в долге сидит вся история расчётов (у Кристалла разница 2,5 млн). **Договоров (как в 1С) у нас нет и не нужно** — долг на контрагенте, движение в документах. **Начальные остатки ДЕНЕГ заведены 13.11.2026** — `cash_accounts.opening_balance` + `opening_as_of`: баланс счёта = нач. остаток + движения С ЭТОЙ ДАТЫ (более ранние уже внутри остатка). Адал Строй 2 на 01.11.2026: Наличные 22 245 955 · Банковский счет 5 296 692,10 · Каспи голд Берик 1 764 826,23. Учтено в `fin.repo.balanceByAccount`, `shift.service` (balOf, accountsOverview, старт месячного свода). Ввод — «Финанс → 🏦 Счета», кнопка ⚖ у счёта (сумма + дата). Минус по счёту НЕ запрещаем (решение владельца: «пусть минус, даты не трогай, выровняю постепенно»).

## Карточка-заявка (Улкан)
- Экраны: `incoming → reception → outgoing → accounting → bookkeeping → archive`. Воркфлоу декларативно в `services/orderWorkflow.ts` (TRANSITIONS), диспетчер `POST /api/orders/[id]/action`.
- Закуп `kind='purchase'` (цель Центр-Склад), продажа `kind='sale'`. Позиции: `order_positions`.
- **Получатель закупа = заказчик, а не склад. В КАРТОЧКЕ ВЕЗДЕ ВИДНЫ ОБА: кому заказ и кто его завёл (правило 12.11.2026).** Порядок адресата закупа: (1) **контрагент самой карточки** (`contactId` — админ прямо указал, для кого закуп; было: игнорировался, и прямой заказ ЗКП показывал «Центр-Склад»), (2) заказчики связанных заявок (`procurement_links`, несколько → «Первый +N»), (3) склад `to_warehouse_id` / «Центр-Склад» — это и означает «закуп в запас». Центр-Склад — лишь промежуточный пункт (завели к себе, потом продаём), адресатом пишем его только когда заказчика нет вовсе. **Кто завёл карточку** — поле `createdBy` (журнал `order_history`, запись `create`; `fromName` держит ЗАКАЗЧИКА по правилу «заявка от имени заказчика», поэтому создателя берём отдельно через `order.repo.cardCreators`): показывается подписью «создал …» в кабинете логиста и в карточках админки; имя берётся из сессии вошедшего (пока кабинеты филиалов без своих логинов — там будет имя кабинета). Центр-Склад — посредник: в шапке карточки (`toName`) и в строке позиции показываем заказчика связанной заявки (`procurement_links` → карточка-продажа → её контрагент, иначе `from_name`); несколько → «Первый +N» (полный список — `order.recipients`, подсказка на шапке). Заявок за закупом нет (закуп в запас) → имя склада `to_warehouse_id`, иначе «Центр-Склад». Слои: `order.repo.recipientsByPurchases`/`warehouseNames` → `order.service.withPositions` (поля `toName`, `recipients`, `positions[].recipient`); та же логика в листе смены логиста (`addDeliveryToShift`) и в сводке чатов (`message.service.threads`).
- **Производство (кабинет мастера, филиал) — БЕЗ раскроя:** этап карточки в поле `prod_phase` `''`→`accepted`(Принял)→`working`(В работе)→`ready`(Готов к доставке)→`sent`(Отправлено) — отдельный стейт мастера, не конфликтует со статусом «В работе» головы. Приём: `produceAccept`; смена этапа: `produceStart`/`produceReady`. Отправка логисту **целиком или частями**: `POST /api/orders/[id]/send {posIds?}` → выбранные leg=1 позиции → leg=2, экран `outgoing`; когда leg=1 не осталось → «Отправлено». Позиции в кабинете — в шторке (чекбоксы). Раскрой/Распил/Листогиб/`setProdStage`/`cut_confirmed`/`consumeForCut` УБРАНЫ из потока (материал считается кабинетом листов) — **удалены и из кода**: `setProdStage`, `POST /api/orders/[id]/prod` (заглушка 410), `confirmCut`/`setProdStage` в `lib/api/orders`, бейджи «Распил»/«Листогиб». Очередь кабинета (`BranchPortal.production`) включает ЗК с пустым `prod_phase` на входных экранах — иначе прямой заказ не виден мастеру ни на одной вкладке. Цена изделия в `ProductionWorkbench` обязательна (карточка на 0 ₸ не создаётся). **Отправлено = карточка создана в Исходящих (расходная); ERP-накладная проводится на ДОСТАВКЕ логистом** (чтобы правки логиста — недовоз/брак — попали в документ).
- **Действия карточки (Ф-B, в шторке мастера):** 💳 Оплата (`orders.payment` = Долг/Наличка/Каспи, вся карточка); 📁 В проект (`orders.spec_project_id`, привязка к спец-проекту); ➕ Сплит (`POST /api/orders/[id]/split {posIds}` → выбранные позиции в НОВУЮ ЗК-карточку `prodPhase=accepted`, из исходной удаляются, ≥1 позиция должна остаться). `updateCard` умеет payment/specProjectId.
- **Логист правит перед доставкой:** в Исходящих логист меняет кол-во позиции (тап по кол-ву ✎) и убирает позицию (🗑) — `updatePosition`/`deletePosition`, пока карточка не доставлена (`editBlocked`). Правки попадают в накладную при проведении на доставке.
- **Производственный цикл мастера (лист→товар→база→продажа):** изделия карточки НЕ в начальной номенклатуре — создаются при производстве. Имя изделия = идентичность «{вид} {цвет} {см} см» (напр. «Изделие 9003 15 см», **единая формула `lib/itemName`** — используется в прямом заказе, спец-проекте, «в базу»/«в запас»), по нему рентабельность. **«📦 Внести в базу»** (`producer.service.produceToBase`, POST /api/orders/[id]/tobase): для каждого изделия — создать товар в номенклатуре (`ensureProduct` по имени, goods/Комплектующие) если нет → провести производство (`createProduction`, выпуск +на склад производителя, пока БЕЗ списания листа) → у позиции проставить `product_id`. Продажа (касса) авто-вносит в базу если `product_id` пуст. **Авто-производство:** на `produceReady` («Готов к доставке») диспетчер сам зовёт `produceToBase` — изделия выпускаются на склад, а материал списывается раскроем `consumeForCut` (−целые листы того же РАЛа из `material_pieces`, обрезь ≥4 см в остаток). Сырьё строками в документ производства НЕ пишем — иначе расход задвоится с `material_pieces`. Идемпотентность — `alreadyProduced(cardId)` по записи истории `action='produce'`; при повторном вызове выпускаются только дописанные позиции (без `product_id`). **СОБРАННЫЙ В КАТАЛОГЕ ТОВАР = НОВЫЙ ТОВАР, И ОН ОБЯЗАН ПОПАСТЬ НА СКЛАД (правило владельца 13.11.2026).** Номенклатура — ШАБЛОН (базовые товары, комплектующие «Без цвета»), но как только в каталоге собрали товар по цвету/см («Изделие 7024 19 см», «Изделия №19 белый 0.4мм 9003»), это **отдельный товар**: заводится карточка и по ней идёт движение склада — иначе его нечем продать и некуда двигать. Карточку заводят два места: у Нипы — `producer.service.produceToBase` (`ensureProduct` по `itemName`, выпуск на склад производителя), у ВСЕХ остальных (касса магазина, карточка логиста) — `invoice.service.ensureVariantProduct` при проведении накладной: ищем БАЗОВЫЙ товар, чьё имя — начало имени позиции (самый длинный), копируем его дерево/ед./тип, `price_in` = `cost_price` строки иначе закуп базы, владелец — `ownerOrgFor(orgId)`. Базы нет — строка по-прежнему не идёт в документ (ничего не выдумываем). До 13.11.2026 такие строки МОЛЧА выпадали из накладной: деньги в кассу шли, склад не двигался (4 чека Кристалла «Изделия №19 белый 0.4мм 9003», 19 шт). Цвет/см/цена/**себестоимость** всё равно живут в СТРОКЕ (`order_positions.cost_price` = ширина_см × ₸/см). Лист списывается раскроем как раньше. Отчёты день/месяц (`shift.service`) берут себестоимость из `cost_price` строки, иначе `products.price_in`. Голое «Изделие» без РАЛ/см производство пропускает. Только Нипа (`producer_seller`) производит; магазин/головной — нет. ⏳ Полный zero-stock (изделие вообще без движения склада, только материал) и реконсиляция старых остатков изделий — Этап 3. По РАЛ вызывается ровно ОДИН лист того же цвета (`consumeForCut`/`optimizeCut`, 125 см/лист). **Себестоимость = ОДНО число ₸ за 1 см** (`prod_settings.cost_per_cm`, своё на орг; плашка «💰 Себестоимость 1 см» сверху экрана «Производство» — ввод цены листа 1,25×2 м ЛИБО цены за м²): `1 см = цена листа ÷ 125 = цена м² ÷ 50`, себестоимость изделия = **ширина_см × ₸/см** (на 125 второй раз НЕ делить). Цвет на цену ЗАКУПА не влияет (решение владельца 09.11.2026) — старый подбор листа по РАЛу (`sheetForColor`/`pricePerSheet`) удалён совсем; цены ПРОДАЖИ по цветам различаются — отдельная задача. Слои: `prodSettings.repo` → `producer.service.getCostPerCm/saveCostPerCm` → `costPerCmSchema` → `/api/production/cost` (GET/POST) → `lib/api/docs` → `ProductionScreen.CostPerCmBar`. Формула цвета в `producer.service.ralOf` обязана совпадать с `material.service.sheetColor` (РАЛ или «дерево»). **Рентабельность по товару** (`finance.service.profitByProduct`, GET /api/branch/profit, вкладка «📈 Рентабельность» в кабинете): за период по каждому товару выручка − себестоимость (FIFO закупа + непокрытая ×price_in) = прибыль, маржа %. Существующий profitReport уже берёт себестоимость непокрытой части из `price_in` — потому изделия попадают корректно.
- **Касса мастера (Ф-C1) — прямая продажа без логиста:** в шторке нал/каспи/долг(авто)/сдача; «💵 Оплатить» (`services/cashier.service.payCard`, POST /api/orders/[id]/pay) проводит расходную (`postOrderInvoice` → у головного авто-приходная по мосту `orgRefId`), пишет нал/каспи в `payments` (счета филиала = как в ГО: «Основная касса»/«KASPI GOLD»/«Банковский счет»), долг=дебиторка, контрагент=заказчик иначе мост на головной (долг на головной). Карточка `prod_phase='sold'` → секция «💵 Продано». «↩ Отменить продажу» (`unpostSale`, DELETE) = сторно док + удаление оплат + карточка снова в работу (владелец правит после). Поля `orders.paid_cash/paid_kaspi/change_sum/change_from`.
- **Смена мастера (Ф-C2):** вкладка «💵 Смена» (`services/shift.service`, `/api/branch/shift`): доходы (продажи нал/каспи/долг за день по дате расходной накладной), производство в запас (docs production output за день), **расходы через «Деньги»** — ЗП (сотрудник+счёт+ручная сумма оклада, article='ЗП') и текущие (`fin_rows` с отрицат. суммой через `saveFinRow`), остаток по счетам, «Закрыть смену» (`postFinDay`). Ставку сотрудника НЕ храним — вводят руками. **Деньги меж орг:** инкассация филиал→ГО (`remitToHQ`, нал→Осн.касса ГО, каспи GOLD→Банк ГО) и обратный **возврат от головного** (`returnFromHQ`, POST action `returnHQ`: выбрать свой счёт + сумму → пара проводок, у ГО расход на обратный мост, у филиала приход на счёт — чтобы заплатить ЗП после сдачи выручки); у обеих есть отмена за день (`remitUndo`/`returnUndo`). Строки сами видны в листе «Деньги» обеих орг (авто-строки из payments).
- **Касса продавца (филиал-МАГАЗИН, kind=`seller`) — рабочее место кассира с телефона:** кабинет `/branch/[slug]` ветвится по виду орг (`refs.repo.orgById`): `producer_seller` → `BranchPortal` (стол мастера), `seller` → `SellerPortal` (касса). Продавец жмёт «📖 Каталог» (тот же `NomPicker`: цвет → размер → кол-во), правит кол-во/цену в чеке и пробивает одной кнопкой: `POST /api/branch/sell` → `cashier.service.sellDirect` = карточка-продажа в книге филиала (screen `bookkeeping`, статус «Доставлено») + `payCard` (расходная, склад филиала −, оплаты нал/каспи/QR, остаток = долг). Покупатель по умолчанию — контрагент «Розничный покупатель» филиала (создаётся при первой продаже), выбор другого — по кнопке (`ContragentPicker`). Цены из каталога (`GET /api/pricing`, для изделий — за см), продавец правит в строке. **Производства у продавца нет:** `produceToBase` и цепочка долга через головной в `payCard` работают ТОЛЬКО при orgKind = `producer_seller` — у магазина долг остаётся его дебиторкой, товар берётся из номенклатуры (`ensureProduct` по имени + `ensureProductIdsByName` при проведении). Вкладки: 💵 Касса · 🧾 Чеки (журнал + возврат) · 💳 Долги. **«➕ Прочий доход» — галочка сверху вкладки «Касса»** (как в «Расчёте»): счёт нал/каспи/QR + сумма + «за что» → `otherIncome` (`POST /api/branch/other-income`), деньги на счёт, прибыль 50/50 с головным, склад и накладные не трогаются; в журнале дня строка со своим номером `ПД-NN-DDMMYY`. Работает при пустом чеке — позиции не нужны.
- **Долг только на выбранного покупателя:** если продажа оставляет долг (`net − оплачено > 0`) и покупатель не выбран (Розница) — касса блокирует и открывает выбор контрагента (нельзя оформить долг на аноним). 
- **Вкладка «Долги» магазина = 2 под-вкладки:** «💳 Долг клиентов» (чеки с остатком — текущее, см. ниже) и «📦 Долг товаров» (взяли у соседа товар в долг — вернём товаром). Покупатель/сосед — ТОЛЬКО контрагенты своей орг (`cags` = `c.orgId===user.orgId && !c.orgRefId`, головной/мосты исключены — долги Кристалла «кроме Адал Строй 2»).
- **«📦 Долг товаров» — ОТДЕЛЬНЫЙ журнал, НЕ трогает склад/бухгалтерию. ДВЕ стороны:** таблица `goods_debts` (orgId+contragentId, qty numeric scale 3 — дробное), direction 4 типа: **мы должны** `take` (взяли у соседа)/`return` (вернули ему); **нам должны** `give` (отдали соседу в долг)/`giveback` (сосед вернул нам). Остаток по товару (имя+ед), на КОЛИЧЕСТВО (не деньги): `weOwe=Σtake−Σreturn`, `theyOwe=Σgive−Σgiveback`. Слои: `goodsDebt.repo`/`goodsDebt.service` (`listGoodsDebts` → `{entries, balances[{contragent, items[{productName,unit,took,returned,given,givenBack,weOwe,theyOwe}], weOweTotal, theyOweTotal}]}`; `addGoodsDebt` 4 направления + `contragentInOrg`; `deleteGoodsDebt`), роут `GET/POST/DELETE /api/branch/goods-debt`, dto `goodsDebtSchema`, api. UI в `SellerPortal`: шапка с итогами «мы должны»/«нам должны», 2 кнопки «➕ Взяли в долг»(оранж)/«➖ Отдали в долг»(синий `BLUE`); форма (сосед `ContragentPicker` только свой + товар через `NomPicker`-каталог + кол-во дробное + ед.); свёрнуто по соседу → товары с под-строками по каждой стороне («↩ Вернул» dir=return / «↩ Принял» dir=giveback); раскрытие = журнал (взял/вернул/отдал/принял) с 🗑. Остаток `max(0,…)` — переплата в минус не уходит.
- **Погашение долга (касса магазина):** вкладка «💳 Долги» → «Долг клиентов» — список чеков с остатком долга (`checkDebt = cardTotal(net) − paidTotal`), сумма всего долга, выбор счёта прихода, поле суммы (пусто → весь остаток) + «💵 Погасить». Погасить можно и из шторки состава чека. Погашение — шторка со **смешанной оплатой** (сумма по каждому счёту). Бэкенд `cashier.service.payDebt(cardId, splits[{accountId,amount}])` (`POST /api/branch/debt`, поле `splits`): по каждому счёту приход (`payments direction='in'`), привязка к документу чека → остаток долга (`net − Σ payments in`) уменьшается; итог клампится к остатку (лишнее по порядку счетов не пишется). `withPositions` отдаёт `paidTotal` (Σ приходов по документу чека).
- **Вкладка «🧾 Чеки» магазина — журнал + возврат:** фильтр по дню (кнопка «Сегодня» + `<input date>`, по умолчанию сегодня), итог дня (`daySum`). Каждый чек: № накладной (`docNumber`), время, продавец, покупатель, способ оплаты, кол-во позиций, сумма (считается из `positions` — в `orders` поля total НЕТ, `cardTotal`). Возвращённые чеки помечены (перечёркнуты, бейдж «возврат», `↩ возвращено X`). Кнопка «↩ Возврат» открывает шторку: чекбоксы позиций + **редактор КОЛ-ВА к возврату** (степпер −/+/ввод, клампится к остатку `продано − уже возвращено`; полностью возвращённые заблокированы), «Весь чек»/«Снять всё», выбор **счёта возврата** (`cashAccounts` филиала), предпросмотр «к возврату» и «со счёта». Бэкенд `cashier.service.returnSale` (`POST /api/branch/return`, dto `returnSchema`, вход `items:[{posId,qty}]` — пусто → весь остаток чека): по выбранным позициям/кол-ву создаёт **возвратную накладную** `createReturn(..., 'return_in')` (товар +склад филиала частичным кол-вом, −долг заказчика), затем деньги — **сначала гасит текущий долг чека**, остаток `refund = max(0, R − долг)` возвращает со счёта (`payments direction='out'`, `comment='Возврат {cardId}'`). Долг считается с учётом прошлых возвратов (`prevRet − prevRefund`). Возврат сверх остатка позиции клампится, исчерпанные отклоняются (по сумме `qty` в `source_pos_id` проведённых return_in). Исходная продажа НЕ трогается — возврат отдельным документом (учёт цел). `withPositions` отдаёт `docNumber`/`returnedSum`/`returnedByPos` (возвращённое кол-во по позиции). Старая кнопка «Отменить продажу» (`unpostSale`) в кассе магазина ЗАМЕНЕНА возвратом (полное сторно = возврат всех позиций).
- **ЦЕНА ВОЗВРАТА = СЕБЕСТОИМОСТЬ (правило магазина Кристалл, 10.11.2026):** товар принимаем обратно НЕ по цене продажи, а по себестоимости единицы (`order_positions.cost_price` строки, иначе закуп `products.price_in`; у изделия цена за см — себестоимость штуки делим на см; себестоимости нет (0) → откат на цену продажи, иначе приняли бы за 0). Кассир может **вписать свою цену** в строке шторки возврата (поле «Цена возврата», ↺ возвращает себестоимость, подпись «цена изменена вручную · себестоимость N»). Деньги: сумма возврата сначала гасит долг чека, остаток уходит со счёта (`payments direction='out'`) — **касса в минус** (в шторке строка «Касса минус −N ₸»). В «Кассе дня» отчёт дня показывает строку «Возврат (по себест.)», итог дня = `продажа − возврат − ЗП − расходы` (`masterShift.report.ret/refund`; обмены по чеку из суммы исключены). Слои: `returnSchema.items[{posId,qty,price?}]` → `cashier.service.returnSale` (`costPriceOf`/`retPriceOf`) → `POST /api/branch/return` → `lib/api/orders.returnSale` → `SellerPortal`; себестоимость единицы приходит с позицией как `unitCost` из `order.service.withPositions`.
- **Обмен по чеку (касса магазина):** покупатель принёс товар и берёт другой — ОТДЕЛЬНАЯ операция сегодняшним днём, **только на РАВНУЮ сумму** (решение владельца 08.11.2026). Правка чека для этого не годится: она сторнирует накладную и переносит выручку на день правки. Исходный чек не трогаем (остаётся в отчёте своего дня); сданное — возвратной накладной на склад (`createReturn ... return_in`), выданное — расходной (`createSale`), обе с комментарием `Обмен по чеку {cardId}`; **денег не двигаем** — кредит возврата гасит долг расходной, сверка дня сходится (продано +X, возврат −X). Суммы не сошлись → касса не проводит и пишет разницу. Слои: `exchangeSchema` → `cashier.service.exchangeSale` → `POST /api/branch/exchange` → `lib/api/orders.exchangeCheck` → `SellerPortal` (кнопка «🔄 Обмен» в журнале и в шторке чека, шторка «сдали/выдали»). `withPositions` отдаёт `exchangeSum/exchangeDate/exchangeIn/exchangeOut` — чтобы обмен не читался как возврат (бейдж «обмен ДД.ММ», строка «сдано → выдано»; в «возвращено» обмен вычитается).
- **Правка пробитого чека (касса магазина):** в шторке чека кнопка «✏️ Изменить чек» (пока по чеку НЕТ возврата) — меняются кол-во, цена, состав (🗑 убрать, «＋ добавить из каталога» через `StoreCatalog`), счета оплаты (нал/каспи/QR) и скидка. Бэкенд `cashier.service.editCheck` (`POST /api/branch/check`, dto `editCheckSchema`): сторнирует документы чека + удаляет их оплаты → приводит `order_positions` к новому составу (удалить/обновить/добавить, товар по имени через `ensureProduct`) → заново `payCard` (новая расходная, склад и касса пересчитываются, долг = нетто − оплачено). Чек с возвратом править нельзя — сначала отменить возврат. Смоук: 2×1000 нал → правка 5×1200 (нал 3000 + каспи 1000) → склад −5, касса +3000, долг 2000, старый документ `cancelled`.
- **Счёт возврата = счёт оплаты чека:** в шторке возврата счёт подставляется по способу оплаты (нал → Основная касса, каспи → KASPI GOLD, QR → Банковский; смешанная — где больше), рекомендованный помечен ✓ и зелёной рамкой, рядом подсказка «чек оплачен: …». Раньше подставлялся первый счёт списка — из-за этого возврат наличного чека ушёл с банковского счёта.
- **Скидка по чеку (касса магазина):** в шторке чека — переключатель **₸ / %** + поле; итог к оплате = Σпозиций − скидка (`net`, перечёркнутая исходная + нетто). Хранится на заказе (`orders.discountSum`/`discountPct`), проводится в накладную (`createSale` `discountSum` → `documents.total = subtotal − скидка`, `discountPct` инфо), оплаты/долг считаются от нетто (`payCard`). В отчётах «продано» = `sum(qty*price) − discount_sum` (masterShift/cashReport — сверка не ломается). Возврат: база долга тоже за вычетом скидки. `sellSchema`/`sellCheck`/`SellInput` несут `discountSum`/`discountPct`.
- **«🧮 Расчёт» = рабочее место кассира за компьютером** (`CalcScreen`, только орг-магазин): два столбца — слева лист сметы, справа **липкая панель «Чек»** (узкий экран <1180px — панель уходит под таблицу). В панели: покупатель (`ContragentPicker`), продавец (тот же ключ `u2b_seller_{orgId}`, что у кассы), код чека, **скидка ₸/%**, крупный «К оплате» = Σпозиций − скидка, **СМЕШАННАЯ оплата** (нал/каспи/QR/долг — сумма в каждой строке, кнопка «всё»/«остаток» добивает до итога), сверка «✓ распределено / осталось распределить / перебор» (пока не сошлось — кнопка неактивна), «Дали нал» → сдача, «Пробить чек» + горячая клавиша **F9**. Долг — только на выбранного покупателя; бонусные строки (товар соседа) без цены соседа и «у кого взяли» не пробиваются. Бэкенд тот же, что у кассы магазина: `sellCheck` → `cashier.sellDirect`; долг отдельным полем не шлётся (считается как нетто − нал − каспи − QR), сдача уменьшает внесённый нал в `payCard`. В строке ИТОГО — количество и число позиций.
- **Продавец за кассой (магазин):** при первом заходе с телефона касса спрашивает «Кто за кассой?» — список сотрудников филиала (`employees`, у Кристалла заведены Аслан и Нурбол, должность «Продавец»). Выбор хранится на устройстве (`localStorage` `u2b_seller_{orgId}`) и держится, пока не нажмут «сменить» в шапке. Чек пишет продавца в `orders.seller_id`/`orders.seller` (+ `from_name` = имя продавца, чтобы чек был подписан в списках) — отсюда отчёт «кто сколько продал». Список сотрудников ведётся в админке (Сотрудники, орг = филиал).
- **Журнал чеков магазина («Касса дня»):** у филиала-магазина продажи собираются ЧЕКАМИ, а не только расходными накладными — в `/admin/cashday` блок «🧾 ЧЕКИ ДНЯ» (над счетами): время · номер накладной · продавец · покупатель · кол-во позиций · способ оплаты (+ долг) · сумма; клик раскрывает состав чека (позиция, кол-во×см, цена, сумма, сдача). Данные — `shift.service.masterShift` → `cards` (+ `seller`, `docNumber`, `ts`, `cnt`, `lines` одним запросом по всем чекам дня).
- **ДОХОДЫ «Кассы дня» = ФАКТ ПО СЧЕТАМ (правило 11.11.2026):** ячейки Наличка/Каспи(GOLD)/QR(банк) показывают **приход по счетам за день из `payments`** — то же, что видно в «Деньгах»/финансах, включая погашения долгов прошлых дней и прочий доход; под каждой мелко «по чекам N». Раньше брались снимки `orders.paid_*` чеков дня, и любое более позднее движение (погашение долга, прочий доход, правка) в ячейки не попадало — цифры расходились с финансами. Отдельной строкой показываем, чем приход отличается от продаж: «погашение долгов», «прочий доход», «ушло со счетов (возвраты/инкассация)». Сверка «нал + каспи + QR + долг = продано» осталась ПО ЧЕКАМ (подпись «по чекам»), «Продано» и отчёт дня (наценка/ЗП/итог) считаются по чекам как раньше. Слои: `shift.service.masterShift` → `income.fact { cash, kaspi, qr, total, byCheck, debtPay, otherIn, out }` → `CashDayScreen`.
- **Отчёт дня «Касса дня → День»** (`masterShift.report`, блок «📄 ОТЧЁТ ДНЯ» в `CashDayScreen`) — по образцу Excel «Отчет дня», считается на лету (при закрытии смены данные уже в отчёте): **ПРОДАЖА** (продано=`income.total` · **наценка**=продано−себестоимость по `price_in` · долг · приход нал/каспи/QR) · **РАСХОД** (**ЗП** каждого продавца = `оклад (employees.daily_wage) + 40%·наценка ÷ N`, где продавцы = кто пробил чек в этот день по `orders.seller`; + расходы магазина=`currentTotal`) · **ИТОГ** = продажа − ЗП − расходы. `report = { sold, margin, marginPct, cash/kaspi/qr, debt, sellers[{name,oklad,bonus,zp}], zpTotal, shopExp, result }`.
- **Месячный свод «Касса дня → Месяц»** (`shift.service.cashReport`, вкладка «Месяц» в `CashDayScreen`) — по образцу Excel-отчёта производства (`отчет ... .xlsx`): по дням секции ТОВАРНАЯ ЧАСТЬ (Продано/Возврат=`return_in`/Долг) · ПРИХОД (Нал/Каспи/QR) · сверка ✓ · **МАРЖА** (маржа=`отпуск − себестоимость` по `products.price_in`, деление **60%/40%**) · **ЗАРПЛАТА** (ЗП + `ЗП+40`=ЗП+40%·маржа) · Расход · **ОСТАТКИ СЧЕТОВ нарастающим** (конец дня = старт + движения ≤дня; старт на 1-е число = все `payments`+`fin_row_amounts` ДО периода, авто из истории). `cashReport` отдаёт `days[]` (+`ret/margin/split60/split40/zpPlus40/bal`), `accounts`, `opening`, `endBal`, `totals`. Формула маржи/60-40/ЗП+40 — предположение по Excel, при расхождении править в `cashReport`.
- **Спец-проект мастера** (кабинет, вкладка «🎨 Спец проект»): собрать список моделькой → раскрой → «К логисту» (частями) минуя производство. Бэкенд `carveToLogist`.

## Проекты (call-off) и материал/спецификации — см. память `[[material-spec-model]]`, `[[projects-drawdown-model]]`
- **Проект** = мастер-список (`spec_projects` + `spec_project_items`), из него **выносим карточки по частям** (`carveCard`), остаток = qty − Σ(вынесено по `order_positions.spec_item_id`). Раздел админки «📁 Проекты».
- **Спецификация:** `spec_types` (тип изделия → стандартный см: Н=18, J=8, углы 11/25), `products.specTypeId`. Комплектующие = **13 базовых товаров «Без цвета»**; конкретное изделие собирается в модельке (**база + цвет + см → имя «Изделие 7004 26 см»**, `productId`=база для отчётов). Пикеры: `NomInline` (инлайн), `NomPicker` (каталог), быстрый набор `lib/nomTree` (accessoryKinds, «Изделие» с `measure`).
- **Склад материала** = физические КУСКИ (`material_pieces`), НЕ м²: лист 125×200 (`kind='sheet'`), обрезь = полоса по ширине (`kind='remnant'`), **обрезь <4 см (`MIN_REMNANT_CM`) → в расход**. Раздел «🧱 Материал» (типы / склад-ревизия / привязка). Приход листов — из приходной накладной; на складе только ревизия. Раскрой: `lib/production` (`optimizeCut`, режем по ширине 125). Матчинг листа: по цвету, только НЕ матовый, толщина неважна. ⏳ Ф2 (раскрой↔склад) — не построено.

## Рабочие правила (важно!)
- **🔎 ПОИСК — ПО СЛОВАМ, А НЕ ПО ПОДСТРОКЕ (правило 11.11.2026).** Любое поле поиска ищет так: каждое слово запроса должно встретиться где-то в тексте (начало, середина, конец), порядок не важен, регистр и ё/е не важны. «евро 7024» обязано находить «Евро брус МП RAL7024 0,4мм». Единый хелпер — `lib/search.ts` (`matchWords(q, ...поля)` / `filterByWords`), и в новых экранах использовать ТОЛЬКО его, без `includes(подстрока)`. Уже переведены: каталог кассы (`StoreCatalog`, `SellerPortal`), `NomInline`, `ContragentPicker`, формы накладных (`DocCreateForm`), Номенклатура, Склад, Производство, Материал, Фильтр, У-Канбан, Бухгалтерия, поиск карточек в шапке.
- **Каталог за компьютером (ширина ≥1000px, `StoreCatalog`):** поле кол-ва стоит СРАЗУ за названием (имя не растягивается на всю ширину, `flex: 0 1 480px`), между ячейками кол-ва ходим **стрелками ↑/↓ и Enter** (`data-qty-cell` + `qtyKey`, фокус сам выделяет значение), а выбранное — аккуратным списком **справа** (340px: позиция, кол-во, ✕, «очистить», «Готово») вместо нижней полоски. На телефоне раскладка прежняя — кол-во справа и нижняя панель «Выбрано … Готово».
- **СУММУ СТРОКИ В НАКЛАДНОЙ ВПИСЫВАЕМ РУКАМИ (правило 11.11.2026).** Накладная завода даётся суммами, поэтому в форме колонка «Сумма» — поле ввода: вписал сумму → цена считается обратно (сумма ÷ кол-во), а в документ уходит **ровно вписанная сумма**, не `кол-во×цену` (иначе копейки теряются и итог не сходится с накладной поставщика). Правишь кол-во или цену — сумма пересчитывается. Деньги в форме показываем **с двумя знаками** (`ххх,00`), шаг ввода 0,01. Слои: `purchaseLineSchema.amount?` → `document.service.createPurchase/createSale` (`amount` берётся как есть, иначе `lineAmount`) → `InvoiceForm` в режиме создания (`setQtyL/setPriceL/setAmountL`, `m2`).
- **СОЗДАНИЕ НАКЛАДНОЙ = ТА ЖЕ ФОРМА, ЧТО У ПРОВЕДЁННОЙ (правило 11.11.2026).** Отдельной формы создания НЕТ (старый `DocCreateForm` удалён): «+ Создать приход/расход» открывает `InvoiceForm` в режиме создания (`createKind` + `orgId` вместо `id`) — та же утверждённая шапка (номер/дата/контрагент/склад/вх.номер/вх.дата/операция/комментарий), блоки «накладная поставщика», колонки №/Номенклатура/Кол-во/Ед./СМ/₸/шт/Сумма/Коммент, скидка, вкладка «Оплата», Подытог/Всего. Добавлено: **📖 Каталог** (тот же `StoreCatalog`, что у кассы) + поиск по словам, **ПОЛУЧАТЕЛЬ** прихода, редактируемые кол-во и **сумма строки**. Товара нет в номенклатуре → строка не добавляется (нужен `product_id`), форма пишет какой. Новые поля шапки/строк принимает `createPurchaseSchema` (number/inNumber/inDate/operation/discount*/paidSum, в строке name/widthCm/comment/block).
- **🁢 ПРАВИЛО ДОМИНО (главное, 11.11.2026).** Система связанная: одно действие валит соседние костяшки. Прежде чем менять/удалять что-либо, пройти по цепочке и выписать последствия — **есть последствия → СПРОСИТЬ владельца до того, как делать**, а не после. Типовые цепочки: позиция карточки → накладная → склад → долг контрагента → отчёт дня/месяца → зеркало другой орг (`parent_doc_id`) → автозакуп (`procurement_links`) → себестоимость (FIFO `doc_links`) → ЗП от маржи. Дата документа тянет: движения склада → остаток на дату → касса дня → закрытая смена. Смена контрагента тянет: долг → цепочку головного (сторно зеркал). Удаление/перенос поля экрана тянет: кто им пользуется в другом кабинете. В ответе владельцу честно называть, что ещё поедет, даже если он не спрашивал.
- **«Закоммить» = commit + push вместе** (ветка master), без переспрашивания. Доводить задачу до конца/задеплоя.
- Каждый значимый шаг: **`tsc --noEmit` → `next build` → смоук → commit → push**. Обновлять план-файлы и память.
- Отвечать **кратко**, без длинных перечней опций. Уточнять только когда реально меняет план.
- Смоук: минтить JWT (`jose`, cookie `u2b_session`, секрет из `.env.local`) + бить по `localhost:3000`; чистить тест-данные после; убивать лишние `next dev` (порты 3000+).
- Схема БД: правка `src/db/schema.ts` → `npx drizzle-kit push --force`.
- **Bash-инструмент = Git Bash (POSIX)**, НЕ PowerShell: НЕ использовать here-string `@'...'@` (лезет `@` в коммит) — сообщения коммита через файл `-F`. Временные скрипты — в scratchpad или удалять после.
